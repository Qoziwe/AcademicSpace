# Требования к разработке фронтенда

> Копия исходных требований, предоставленных пользователем, дословно.

При разработке фронтенда необходимо учитывать следующие факторы:

1. Фронтенд пишется строго на React Native (на TypeScript, используется
   Expo), для создания кроссплатформенного кода, который пойдёт как
   приложение на мобильные устройства (iOS/Android), так и на ПК в
   качестве веб-сайта. Дизайн должен быть адаптивным для всех устройств.
2. При написании кода следует строго категоризировать каждый раздел (всё
   должно быть упорядочено).
3. Все секреты прописываются в `.env`. Все публичные ключи и URL
   прописываются в `.env` с префиксом `EXPO_PUBLIC_`.
4. Должно быть несколько главных файлов с конфигами.
5. Перед началом разработки следует создать отдельный md-файл с
   полнейшим, наидетальнейшим идеологическим и визуальным описанием
   дизайна (обсудить с пользователем), с помощью которого будет
   писаться дальнейший фронтенд.
6. Перед началом разработки необходимо также создать единую цветовую
   палитру в двух вариациях — тёмное/светлое, указать семейство шрифта,
   указать размеры всех типов текста (заголовки, подзаголовки), углы
   наклонов, углы скругления блоков. Везде должен быть стандарт, на
   который нужно опираться при вёрстке страницы.
7. При проектировании фронтенда какой-либо страницы необходимо
   ссылаться на инструкции из пунктов 5, 6, чтобы все страницы
   приложения имели единый стиль и не различались друг от друга — нужно
   полагаться на единый UI-кит.
8. Самое важное для написания кода. Код обязан быть структурирован
   грамотно и чётко — атомарный дизайн. Необходимо создать отдельно
   каждую модель интерфейса и потом как пазл собирать интерфейс из
   заготовленных блоков — таким образом код от страницы к странице
   меняться не будет и везде будет использоваться единый стандарт.
9. Необходимо учесть, что фронтенд на React Native будет подключён к
   бекенду, написанному на фреймворке Flask, то есть проектировать
   структуру под это.
10. При создании функции, обращающейся к бекенду, необходимо вносить
    используемый url/api в отдельный md-файл в корневой папке, чтобы
    потом бекендер составлял функции специально под эти URL, в формате:
    ```
    *** Метод: GET
    *** URL: /api/v1/users
    *** Отправляем: token
    *** Ожидаем получить: [{id, name, avatar}]
    ```
11. State management — для работы с API (серверным состоянием) строго
    TanStack Query. Для локального состояния приложения (UI, токены,
    тема) — Zustand.
12. Проект должен быть строго настроен с ESLint и Prettier.
13. Не должно быть ни одной нефункциональной кнопки, не должно быть
    выбивающихся из общего стиля деталей, не должно быть мусорного
    захламления интерфейса множеством кнопок и так далее.
14. Работа с Git и репозиторием. Прямые пуши в `main` запрещены — строго
    Feature-Branch Workflow. Внедрить Husky + lint-staged (код с
    ошибками линтера физически блокируется на этапе коммита).
    Именование коммитов строго по спецификации Conventional Commits.
    Слияние веток в GitHub осуществляется исключительно через Pull
    Requests методом Squash and Merge для поддержания абсолютно линейной
    истории репозитория без мусорных коммитов.
