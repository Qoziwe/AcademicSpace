# Алгоритм подбора вузов (Фаза 10)

Реализация — `backend/app/services/matching/` (`config.py` — все числа,
`normalize.py` — перевод разнородных шкал в индекс 0–100,
`scoring.py` — чистая математика, `service.py` — оркестрация с БД).
Юнит-тесты формулы — `backend/tests/test_matching_scoring.py`, интеграция
анкета → подборка — `backend/tests/test_matching_service.py`.

## Почему не байесовское сужение («Акинатор»)

Akinator сужает одну неизвестную гипотезу через серию да/нет вопросов. У
нас нет одной скрытой цели — есть N вузов, и для каждого нужно независимо
оценить вероятность поступления по нескольким непрерывным шкалам сразу.
Это задача скоринга (ближе к college-chancing калькуляторам или кредитному
скорингу), а не поиска — поэтому формула ниже взвешенная, а не
байесовская. Общая с «Акинатором» интуиция «очки копятся с каждым
ответом» сохранена: каждое поле анкеты даёт вклад в итоговый fit-score.

## 1. Нормализация входа

`GPA` и балл профильного экзамена анкета собирает уже в шкале 0–100
(просим пользователя самого перевести в проценты) — конвертация не
нужна. Языковой сертификат — в родной шкале теста (IELTS 0–9, TOEFL
0–120, Duolingo 10–160), переводится в индекс 0–100 линейной
интерполяцией (`normalize.language_index`). "Не сдавал" → честный 0, а
не нейтральные 50 — отсутствие подтверждённого уровня не должно
маскироваться под «средний результат».

## 2. Fit-score — логистическая кривая, не линейный обрыв

Для каждого критерия `delta = индекс_ученика − требование_вуза`:

```
sub_score(delta) = 100 / (1 + e^(-k·delta/10))      k = LOGISTIC_K (1.0)
```

При `delta = 0` (ученик ровно на уровне требования вуза) `sub_score = 50`
— это осознанно «монетка», а не гарантия поступления: попадание точно в
средний балл поступивших в реальности не даёт стопроцентной уверенности
ни в одну сторону. Положительный запас плавно тянет к 100, недобор — к
0, без искусственного обрыва на пороге, который давал бы ложную
уверенность у границы.

```
fit_score = 0.40·sub_score(ΔGPA) + 0.35·sub_score(Δэкзамен) + 0.25·sub_score(Δязык)
          + interest_bonus (+5, если факультет вуза совпадает с интересами анкеты)
          + achievement_bonus (+1.5 за каждое достижение, максимум +6)
```

Веса/бонусы/`k` — только в `config.py`, калибровка не трогает
`scoring.py`.

## 3. Корзины Safety / Match / Reach

Базовые пороги (для «нейтрального» вуза, `selectivity_tier = 3`):

| Порог | fit_score |
|---|---|
| Safety | ≥ 80 |
| Match | ≥ 55 |
| Reach | ≥ 30 |
| — (не показываем) | < 30 |

`selectivity_tier` вуза (1 — топ, тяжело поступить; 5 — почти без
отбора) сдвигает пороги именно для этого вуза: `shift = (3 − tier) × 5`.
Топовый вуз требует более высокий fit-score, чтобы считаться «safety»;
у вуза с низким отбором планка ниже. Вузы с fit-score ниже порога Reach
не показываются вовсе — нечестно выдавать недостижимый сейчас вариант
без контекста «зоны роста».

Показанный `chance%` — тот же fit-score, заклэмпленный в 5–97%, чтобы
не создавать ложной уверенности на краях шкалы.

## 4. Жёсткие фильтры (до скоринга)

Вуз вообще не попадает в кандидаты, если не совпадает по стране,
выбранному факультету (`university.faculties`), языку обучения
(`university.languages_offered`) или стоимость выше заявленного
потолка бюджета (`preferences.costMaxEur`). Это чистая фильтрация по
каталогу, не часть формулы.

**Известное ограничение v1**: шаг фильтра «Университеты» (шорт-лист
конкретных вузов) не используется как жёсткий фильтр — его опции на
фронте статичные и не связаны с реальным каталогом по стране. См.
`docs/api-contract.md` §Questionnaire.

## 5. Рейтинг абитуриента (`Profile.rating`)

Тот же взвешенный индекс, что и в fit-score, но сам по себе — без
сравнения с конкретным вузом (`scoring.student_composite_index`):

```
rating = 0.40·GPA_index + 0.35·экзамен_index + 0.25·язык_index
```

Показывается на дашборде/результатах подбора как «рейтинг абитуриента».

## 6. Почему не ML-модель

Исторических данных о реальных поступлениях пользователей нет — обучать
не на чем. Взвешенная формула — осознанно «экспертная система» с тем же
входом/выходом, который в будущем (когда накопится статистика реальных
исходов) можно заменить обученной моделью без переписывания API и
фронтенда.
