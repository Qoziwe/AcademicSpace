# AcademicSpace — инструкции для Claude Code

## 0. Контекст проекта
AcademicSpace — персонализированное приложение для школьников 9–11 классов,
которое помогает выбрать университет и спланировать поступление:
алгоритмический подбор вузов (Safety / Match / Reach), премиум ИИ-анализ
портфолио, ИИ-ментор в чате с интерактивными модулями (дорожные карты /
чек-листы / таймеры), копилка документов, геймификация (100 уровней, XP),
инструменты фокусировки.

Стек: React Native + TypeScript + Expo (Expo Router) — единая кодовая база
под iOS / Android / Web. Бекенд появится позже на Flask — сейчас его нет,
весь фронтенд строится на моках.

## 1. Порядок работы прямо сейчас
Мы на этапе: **конвертация уже готового визуального дизайна в рабочий
фронтенд**. Бекенда ещё нет, и в этой фазе он не нужен. Единственная цель
ближайших фаз — 24 (фактически 30, см. `docs/screen-inventory.md`) экрана
из дизайн-референса, полностью рабочие на моках, ноль недоделанных страниц.

## 2. Источники истины (по приоритету при конфликте)

## 3. Про design-reference.html — это не обычный HTML
Файл `docs/source/design-reference.html` — это не готовая вёрстка и не
сайт, который можно открыть и «стащить» разметку 1:1. Это экспортированный
из Claude Design canvas-прототип: один JS-класс
(`class Component extends DCLogic`) с самодельным шаблонизатором
(`sc-if`, `sc-for`, `{{ выражения }}`) и рантаймом `support.js`, который
существует только внутри Claude.ai. Он не собирается через npm, там нет
отдельных .css/.js файлов проекта — все стили инлайновые CSS-in-JS строки.

**Что с ним делать:** читать как исчерпывающую визуальную и поведенческую
спецификацию — точные hex-цвета, размеры, радиусы, отступы, копирайтинг,
состояния (`sc-if`), списки данных (`sc-for`), обработчики (`onClick`) — и
**пересобирать вручную, экран за экраном**, на нативных RN-примитивах
(`View` / `Text` / `Pressable` / `ScrollView` и т. д.) + токенах из
`design-tokens.md`. Автоматического парсинга/транспиляции этого файла не
будет и не должно быть — нужна ручная реализация с точным попаданием в
значения.

В самом низу файла, в `renderVals()` (строки ~1191–1564) и классе
`Component` (~1130–1190), лежит вся стейт-машина прототипа (состояние
анкеты/фильтров/чата/задач/оплаты) — это готовая спецификация бизнес-логики
экранов на моках. Переноси её смысл в Zustand-сторы + мок-хуки TanStack
Query, а не только визуал.

## 4. Ребрендинг: UniPath → AcademicSpace
Все 4 исходных документа и сам дизайн-файл используют плейсхолдер-бренд
«UniPath» (название приложения, «UniPath Premium», лого-ромб, deep link
`unipath://`). Реальный продукт называется **AcademicSpace**. Правило:
нигде не хардкодить «UniPath» — весь брендинг (имя приложения, название
тарифа «AcademicSpace Premium», deep link scheme `academicspace://`,
bundle id / package name) вынести в один конфиг (`app.config.ts` +
`constants/brand.ts`), значение по умолчанию — AcademicSpace. Лого-знак
(градиентный ромб) пока оставляем как временный, если у пользователя нет
готового брендбука — уточнить отдельно, если появится.

## 5. Хард-правила стека (из требований пользователя — не отступать)
- TypeScript строго, Expo (managed workflow), Expo Router — файловая
  маршрутизация 1-в-1 на `docs/screen-inventory.md` /
  `docs/source/03-routes.md`.
- Адаптивность: одна кодовая база одновременно под iOS/Android И веб
  (`expo start --web`). Сейчас это значит «не ломается на широком
  экране», а не полноценная desktop-раскладка — она отдельной фазой
  позже, см. §9.
- Секреты — только `.env`, публичные ключи/URL — с префиксом
  `EXPO_PUBLIC_`. Коммитить `.env.example`, не `.env`.
- Атомарный дизайн: `components/atoms`, `components/molecules`,
  `components/organisms` — переиспользуемые пазл-блоки, а не копипаста
  стилей от экрана к экрану. Каждый визуальный примитив — отдельный
  компонент, использующий только токены из `design-tokens.md`.
- State management: **TanStack Query** — весь «серверный» стейт (даже пока
  это моки за mock-адаптером, интерфейс хуков должен быть таким же, как
  будет с реальным Flask API); **Zustand** — локальный UI-стейт (тема,
  премиум-флаг на этапе моков, состояние форм в моменте, тумблеры).
- ESLint + Prettier обязательны. Husky + lint-staged — блокировка коммита
  с ошибками линта.
- Git: Conventional Commits. Прямые пуши в `main` разрешены для Claude
  Code — не обязательно заводить feature-branch и PR под каждое
  изменение.
- Каждый поход к будущему бекенду документируется в `docs/api-contract.md`
  в формате:
  ```
  *** Метод: GET
  *** URL: /api/v1/...
  *** Отправляем: ...
  *** Ожидаем получить: ...
  ```
  — даже если сейчас за хуком стоит мок, контракт фиксируется сразу, как
  будто бекенд уже есть.
- Ни одной нефункциональной кнопки. Каждый `onClick` дизайн-референса
  должен превратиться в реальную навигацию/действие по
  `docs/source/03-routes.md`.

## 6. Премиум-гейтинг — паттерн уже решён дизайном, просто следуй ему
В прототипе используются **два разных паттерна** в зависимости от места, и
оба нужно сохранить:
1. **Таб-бар** (нижняя навигация): вкладка «Задачи» физически не
   рендерится для Free-пользователя
   (`...(P ? [['Задачи','tasks']] : [])`) — не резервирует место. Так же
   должен работать блок «Активные задачи» на дашборде для Free.
2. **Bento-плитки на дашборде и строки в профиле**: рендерятся всегда, но
   с `opacity` и иконкой замка, и по тапу ведут не на целевой экран, а на
   `PAYWALL` (`tileDefs` / `profileRows` → `lock: prem && !P`,
   `go: () => this.go(locked ? 'paywall' : key)`). Так же работает блок
   документов на `UNIVERSITY_DETAILS` → `REQUIRED_DOCUMENTS` для Free.

Реализуй как переиспользуемый guard-компонент/hook (`usePremiumGate` +
`<PremiumLockTile>`), а не через дублирование условий по экранам.

## 7. Нюанс: реестр роутов vs дизайн-файл
Дизайн-прототип технически рисует несколько роутов из реестра **одним**
визуальным компонентом, переключаясь по внутреннему стейту:
- `AUTH_SIGNUP` + `AUTH_SIGNIN` → один экран с сегмент-контролом
  («Регистрация» / «Вход»).
- Все 5 `FILTER_*` + `QUESTIONNAIRE` → один компонент с шагами 1–6
  (`fstep`).
- `ERROR` / `OFFLINE` / `MAINTENANCE` / `UPDATE_REQUIRED` → один компонент,
  ветвящийся по `sysCopy`.
- `PAYWALL` **включает в себя выбор тарифа inline** (карточки
  «Неделя»/«Месяц» прямо на экране пейвола) и сразу ведёт на
  `PAYMENT_FLOW` — отдельного экрана `PLAN_SELECTION` в дизайн-файле
  физически нет.

Это нормально как источник визуала, но в Expo Router делай **честные
отдельные route-файлы** под каждый ID из реестра (для корректных deep
links, back-behavior и Auth/Premium-гардов из таблицы реестра), а
переиспользуемую визуальную часть выноси в один общий презентационный
компонент (`<AuthForm mode="signup"|"signin">`,
`<FilterStepScreen step={...}>`, `<SystemScreen kind="error"|"offline"|...>`).

Отдельно: `PLAN_SELECTION` (`/subscription/plans`) в реестре нужен для
входа не только с Paywall, но и из `PROFILE_SUBSCRIPTION` (смена тарифа
уже подписанным пользователем) — там маркетинговый экран пейвола не
нужен, нужен только выбор тарифа. Вынеси карточки тарифов из `PAYWALL` в
переиспользуемый молекул-компонент (`<PlanCard>` / `<PlanPicker>`) и
собери из него оба экрана: `PAYWALL` (маркетинг + PlanPicker) и отдельный
`PLAN_SELECTION` (только PlanPicker, без маркетингового блока).

## 8. Тема: светлая/тёмная
В дизайне теперь есть настоящий переключатель темы (Settings → «Тема
оформления»). Токены обеих палитр — в `docs/design-tokens.md`. Важно: в
самом дизайн-референсе тема протянута не по всем экранам одинаково —
файл делит экраны на три группы (полностью на токенах / только внешний
фон / сознательно вне темы, навсегда навy). Точная карта — в
`docs/design-tokens.md`, раздел «Важно: тема применена не везде». При
вёрстке экранов из средней группы (только внешний фон уже theme-aware)
доводи внутренние карточки/текст до того же 7-токенного паттерна
(`page/screen/card/border/ink/sub/chip`), которым уже размечены
Dashboard/Settings/Profile — не изобретай отдельный токен-набор для
конкретного экрана.

Реализация: `theme: 'light' | 'dark'` в Zustand, персистентный через
AsyncStorage, свитч на экране Settings.

## 9. Десктоп-адаптация — отложена
Дизайн пока сделан только под мобильный форм-фактор (телефонный фрейм).
Полноценную широкоэкранную desktop-раскладку делаем **отдельной фазой
после того, как весь мобильный фронтенд по `docs/screen-inventory.md`
полностью готов** — не раньше. До этого момента веб-сборка
(`expo start --web`) должна просто корректно работать и не ломаться на
широких экранах (см. дефолт в `docs/design-tokens.md` — центрированный
app-like контейнер), но специальной desktop-раскладки строить не нужно,
это отдельная будущая задача.

## 10. Definition of Done для одного экрана
Экран считается готовым, когда:
- [ ] Визуал совпадает с `design-reference.html` по цветам/радиусам/
      шрифтам/отступам из `design-tokens.md` (без «на глаз»), включая
      обе темы там, где экран theme-aware (см. §8)
- [ ] Работает и на мобильном размере, и на вебе без поломок (полноценная
      desktop-раскладка — не сейчас, см. §9)
- [ ] Каждая кнопка/тап ведёт куда нужно по `docs/source/03-routes.md`
      (`Destinations` / `Back behavior`)
- [ ] Данные приходят через TanStack Query хук с мок-адаптером (не
      хардкод в компоненте) — контракт зафиксирован в
      `docs/api-contract.md`
- [ ] Локальный интерактивный стейт (чек-боксы, свитчеры, таймер,
      отправка сообщения и т. д.) реально работает, как в прототипе,
      через Zustand
- [ ] Route guard (Auth/Premium) применён согласно колонкам реестра
      роутов
- [ ] Отмечен как готовый (✅) в `docs/screen-inventory.md`

## 11. Чего пока не делаем
- Реальных запросов к Flask (бекенда нет физически)
- Реальной оплаты/платёжного провайдера — просто повторяем стейт-машину
  прототипа (idle → processing → success через `setTimeout`)
- Настоящей авторизации/токенов — мок-сессия в Zustand/AsyncStorage
  достаточно на этом этапе
- Пуш-уведомлений, аналитики — не упоминались в требованиях, не
  добавляем самовольно
- Полноценной desktop-раскладки (см. §9) — до неё дойдём отдельной фазой
  после готового мобильного фронтенда
